# Selected-role execution

Use this shared procedure when the current conversation has an explicit selected role and a current instruction such as “go ahead,” “apply,” “prefill,” “start,” or “network too.” It is a continuation procedure, not a source of permission: first read the current task instruction/history and the live-policy contract required by the invoking Skill. It never authorizes sending, submitting, publishing, account switching, access grants, unrelated destinations, or new sensitive-data use.

## 1. Fix the target and the expected delivery set

1. Retain the explicitly selected employer and role for the whole application bundle. If `next` means continue an explicitly unfinished target, resume it. Otherwise select the next unprocessed role in the agreed explicit queue. Never restart a completed target or choose from an ambient tab; ask one concise target question when no unprocessed target is identifiable. Finish one authorized bundle before advancing.
2. An explicit selected target takes precedence over recommendation preferences. Record a fit caveat or selection exception in existing application history when that write is authorized, without changing global preferences. Do not silently veto, replace, or require a redundant exception request. Classify discovery exclusions by the job's core product responsibility, not isolated AI, ML, data, analytics, or technical-collaboration wording.
3. Treat a caveat as information, not a block. Scoped blockers are a closed role, wrong employer or identity, a duplicate proved by an exact requisition or canonical-role URL match with applicable receipt evidence, a missing material fact, an unsafe destination, or an observed platform block. A same-title historical rejection or uncertain record match is not a duplicate; preserve the uncertainty and ask only if it materially prevents the task.
4. List the application form and every requested outreach recipient before opening or filling pages. This is the expected delivery set. It cannot silently shrink because a tab is absent, a page is hard to reach, or later research finds fewer people. Use the current live policy plus the networking skill's [stakeholder planning](../../ye-company-networking-poc/references/stakeholder-planning.md) for evidence grades, research breadth, activation staging, and stop conditions. Its company-size ranges are soft planning guidance, not quotas or a reason to drop an explicitly requested person.

## 2. Keep a temporary delivery inventory

Keep the following operational inventory in the current task context only. It is transient browser metadata, not a new Notion field, database, durable local business store, or replacement for the existing application/company records. Durable status remains under the existing Notion ownership rules.

| Item identity | Actual returned URL | Browser/tab ID | Component type | Expected state | Observed state | Last in-place readback | Current-turn retention mark | Pending user action |
|---|---|---|---|---|---|---|---|---|
| Employer + role, or exact person | URL actually returned by the page, not a guessed/requested URL | Exact browser and tab/handle ID | Application form, email draft, or invitation composer | `todo`, `in progress`, `ready`, `blocked`, or `user action` | Current visible condition and value evidence | What was read and when in the existing page | `markDeliverable`, `markHandoff`, or unavailable, after the current turn's latest call | Required fact, authority, review, or none |

- Add an inventory row as soon as an expected item is known; update the same row after every material interaction. A returned link, discovered name, or earlier filled value is historical evidence, not a ready deliverable.
- Record each requested recipient by identity even when no composer is open. If a user later confirms an item sent or closed, retain its row and evidence rather than deleting it.
- Treat the expected and observed states as independent. For example, an expected `ready` composer with no accessible tab is observed `missing/unverified`, not ready.

## 3. Validate scope and inspect current state

1. Load the invoking Skill's current live-policy contract, [user standing defaults](user-standing-defaults.md), and relevant records. Reuse the same-day live rules, complete Application Archive, and Company PoC observations while they remain in the active context and no invalidating change has occurred; do not reopen those full pages for each role. Inspect the exact JD and actual application form. Keep application state separate from record-sync state. A search-only request may inspect an ATS page read-only to verify the destination, but does not enter this bundle or permit fields, uploads, drafts, or record writes.
2. When actual task authority covers selected-role preparation, one scoped prefill request can cover necessary official JD and ATS navigation, verified factual field entry using verified known contact facts for that employer application, attachment of the approved correct resume, company and stakeholder research for that role, relevant verified professional profiles, adaptation of the current approved template and filling of unsent outreach composers, and writes to already-authorized existing records.
3. That continuity does not create a consent prompt merely because the operation has multiple clicks or reveals an exact URL. Exact employer ATS URLs and relevant verified professional profiles discovered within the selected-job bundle are not new destinations. An unrelated employer, account, or destination remains outside the bundle; so do new sensitive data, an unknown file identity, a user restriction, and legal or platform action-time requirements. Ask one precise question for a genuinely missing mandatory fact or authority, then continue every independent authorized component.
4. Before interacting with browser lifecycle APIs, read the current runtime documentation. Use only documented capabilities and their current setup requirements; this procedure does not make an unavailable API available or authorize guessing an API across versions.

## 4. Do networking without holding up independent form work

1. Read company PoC knowledge and current known identities. Separately assess current employee/direct-contact or first-degree evidence, known acquaintances, and pertinent mutual-introduction paths; report source, coverage, unique count, and date. An empty PoC record means no recorded evidence, not no LinkedIn connections.
2. From the exact hiring post or JD, apply [stakeholder planning](../../ye-company-networking-poc/references/stakeholder-planning.md). Build a bounded research pool, grade each opportunity-specific association `E1`–`E4`, then activate only the strongest complementary route(s). Keep confirmed responsibility separate from plausible stakeholders and preserve every explicitly requested recipient in the delivery inventory. When the networking check returns evidence, no result, or a genuine scoped blocker, state that exact result and continue independent ATS work.
3. A failed or blocked check stays `blocked` or `unknown`, never done. Missing permission to use an introduction name blocks only that identity or path in outbound content, not neutral cold drafts or the form.
4. Reuse an existing LinkedIn page where possible and navigate each page once per operation. Treat a text-entry capability mismatch on an otherwise healthy, fully ready recipient-specific composer as recoverable: re-observe the same composer and try at most one different ordinary input method when the first attempt neither changed the draft nor triggered Send. Do not reload, change URLs, open a workaround or duplicate tab, switch browsers, construct hidden-profile URLs, or click Send as recovery. Stop LinkedIn for the operation only when the page is blank or still loading, readiness is lost, the recipient is wrong, login/CAPTCHA or a risk block appears, the send state is uncertain, or two distinct ordinary input methods fail. After that stop, renewed user instruction is required. Healthy ATS and Notion components may continue.

## 5. Prepare the application and requested outreach

1. Map only verified facts from the current resume, user-authoritative profile, and validated live rules; preserve chronology and attribution. Collect genuinely missing mandatory answers in one concise batch, then fill every independent field now. Never fabricate an answer.
2. Apply [the user standing defaults](user-standing-defaults.md): salary `Negotiable` for free text, interview-note-taking consent `Yes, I consent` only for that narrow question, accuracy/completeness acknowledgement `Yes` after factual review, offered EEO decline choices, the verified `Ye Xinnan Resume - 2026.pdf`, and user-owned final `Submit`/LinkedIn `Send`. Attach only that verified, authorized resume and read back the visible uploaded filename. A numeric-only salary field or consent outside the stated narrow categories remains user input; never invent or broaden an answer.
3. Load the live Notion template/menu for outreach and use only verified facts, a role-specific CTA, and the current greeting, paragraph, signature, and alumni rules. Apply [outcome-first outreach design](../../ye-company-networking-poc/references/outreach-design.md): choose the desired recipient action first, then one primary candidate signal and at most one supporting signal with correct attribution. Use the canonical current state `considering`, `applying`, `applied`, or `unknown`; reject stale draft wording after a newer application revision. Apply the required language-specific humanizer and conversational `avoid-ai-writing` check before filling external-facing copy; if a required check is unavailable, keep that item pending the check.
4. If the user explicitly requests LinkedIn invitations, use that channel for the requested scope. Otherwise, prefer verified usable email: make a draft only in the authorized correct Gmail account with a verified recipient, subject, body, and composer readback. If no verified usable email exists, use the authorized LinkedIn path; never call an empty-To email ready or substitute paid InMail.
5. For LinkedIn, not connected means Connect then Add a note; already connected permits a follow-up only when requested or supported by scope; pending means no duplicate invite. Follow the networking skill's [LinkedIn delivery contract](../../ye-company-networking-poc/references/linkedin-delivery.md) and state machine. After all writing checks and final edits, use the live initialized composer limit for that exact invitation surface and run the networking skill's `scripts/check_invitation.py` on the exact intended and visibly read-back textarea values. Do not impose a universal 300-character cap; an unknown or uninitialized limit basis is unverified. Email, InMail, accepted-connection messages, and invitations use their own surface contracts. Keep Send untouched.

## 6. Retain review pages safely

The output is currently accessible, user-visible filled review pages: the application form and each requested unsent composer. It is not a list of URLs or evidence that a page was once filled.

1. Prefer an existing exact tab or handle. Bind it and inspect it in place; show it through documented visibility or selection mechanisms, never by `goto` to the same URL, which can reload and clear the form. If a new agent-created page is necessary and the current documentation supports it, create it visibly for the user rather than leaving the deliverable in a hidden working tab.
2. For each ready form or composer, use the documented `markDeliverable()` operation and record the current-turn mark in the inventory. Use documented `markHandoff()` only for unfinished retained work that must continue later. The latest mark wins.
3. On every later browser-active turn, carry forward all still-pending review items, including those not edited in that turn. Reapply the appropriate retention mark to every tab that must survive, after the final in-place readback and before the final response. A prior turn's mark is not evidence of current retention.
4. Never clean up, close, reuse for research, navigate away from, or reload a pending review page. Respect user-owned tabs: do not take ownership of their lifecycle, close them, reload them, or change them merely to make them visible. Use their existing exact handle for an authorized in-place check; report a retention limitation if the documented mechanism cannot safely preserve it.
5. Only research-only disposable tabs may be cleaned up, and only after confirming they are not in the delivery inventory. Never use a delivery tab for research work.
6. An all-pages prefill scope covers the necessary distinct retained application and composer tabs unless the user has imposed a genuine stricter tab limit. If such a limit conflicts with the expected delivery set, preserve the permitted item(s), keep every other item accounted for in the inventory, and report the actual conflict. Do not silently reduce the set.
7. Do not invent a pin API or claim retention when the current documented API is unavailable, its setup fails, a tab cannot be made visible, or survival cannot be ensured. Report the actual limitation and the observed page condition.

## 7. Recover a lost ATS form only within the existing scope

Readiness is volatile. Closing, recreating, navigating, resetting, content loss, or attachment loss invalidates ready status. A user edit makes the affected item require a fresh check; an earlier observation remains historical evidence only.

1. If an ATS form has already lost fields or its attachment, first inspect the current state and exact destination. Check duplicate-submission evidence, verify the same employer, requisition, account, authorized data, and verified same resume file identity, and determine whether a fresh user edit would be overwritten.
2. When those checks preserve the existing scope, restore only the lost ATS fields or attachment and read them back in the actual form without requesting another confirmation for the same authorized data, verified resume, and employer destination. Preserve fresh user edits; ask only about a genuine conflict or newly changed scope. Recovery is not re-submission. Do not use recovery to change the employer, requisition, account, destination, facts, or resume file.
3. A changed fact, account, file identity, destination, or an actual platform/legal barrier is a scoped blocker. Report it rather than treating recovery as blanket permission.
4. This ATS recovery rule never authorizes LinkedIn reopening, alternate URLs, or activity after the bounded LinkedIn recovery above reaches its stop condition. If LinkedIn is stopped, leave the affected item `blocked` or `missing/unverified` and continue only eligible non-LinkedIn work.

## 8. Run focused DeepSeek completion verification when requested

DeepSeek is a final evidence audit for two career deliverables only. Run it once after the application and every requested LinkedIn invitation composer are ready. Build the evidence bundle with exactly these requirements:

1. The application is completely prefilled, the verified resume is attached, and `Submit` remains untouched.
2. Every requested LinkedIn invitation is genuinely visible and recipient-specific, its exact text is present and within the live composer limit, and `Send` remains untouched.

Do not add role liveness, archive deduplication, stakeholder selection or coverage, Notion sync, or general unauthorized-action checks to the career DeepSeek bundle. Those remain local execution responsibilities. If DeepSeek returns a blocking finding, correct that finding and rerun; otherwise do not repeat the audit for the same unchanged role bundle.

## 9. Record durable events separately

For an authorized existing-record write, follow [the shared sync procedure](notion-sync.md), dismiss the editor, and read back the exact destination, changed value, event marker, and preserved state. The application Note/history stores exact per-person text, channel, evidence, and action state; durable company/person knowledge belongs in the company PoC record. Use only the minimal recovery event if a sync fails.

Do not put temporary tab IDs, tab marks, or browser delivery inventory into Notion. A Notion sync failure does not make an otherwise verified browser review page disappear, but it does prevent a global completion claim.

## 10. Reconcile in place before the final response

Do this after all research, cleanup, and record work—not before. Re-bind each expected page by its exact retained tab/handle and perform a fresh in-place readback; do not navigate to the same URL to inspect it.

1. Reconcile the application row: current required fields, selected values, and visible attachment filename. If the page is unavailable, recreated, reset, navigated, or missing its attachment/content, invalidate its ready state and record the observed condition.
2. Reconcile every expected recipient by identity, not just the tabs that remain open. For each composer, verify the displayed recipient/identity and exact final text. For an invitation, verify the textarea recipient/identity and text, the initialized live limit basis, and a successful deterministic invitation check after the latest edit. For email, verify the actual To recipient, subject, and body under the applicable live policy.
3. Verify current visibility/accessibility and the current-turn retention mark for every still-pending review page. Reapply the appropriate mark after this readback. If the bounded LinkedIn recovery reached its stop condition and prevents a readback, do not violate it; mark that item `blocked` or `missing/unverified` with the actual prior error and current unknown state.
4. Account individually for every expected item that is not currently reviewable. In an eight-to-five discrepancy, keep all eight identities: classify each missing three as user-confirmed sent/closed, blocked, missing/unverified, or incomplete, with evidence and next action. Missing is not sent, and closed is not deleted history. Preserve user actions; do not reopen or duplicate pending or sent invitations.
5. Report names with their actual returned links and per-item state. Derive counts from reconciled identities, and never fabricate a claim that the list is complete.

Browser-ready applies only when every still-pending requested review page is actually accessible, user-visible, filled, freshly read back, currently retained, and none is unexplained. Report application/outreach browser readiness and record-sync status separately. If record sync failed, say which browser pages are ready and which durable event is pending; do not claim overall completion.

## 11. Report errors and outcomes precisely

- For an actual tool failure, record the returned error category, observed page condition, and any inferred cause separately; label a cause as inferred when it is not returned or observed. Do not label a text-entry capability mismatch a LinkedIn risk event. When the same recipient-specific composer remains fully ready and no draft or send state changed, the single alternate input method allowed above is ordinary bounded recovery. A page/safety failure, readiness loss, recipient mismatch, uncertain send state, or second distinct input-method failure reaches the stop condition. Report the actual category without inventing a risk diagnosis.
- Report the target, live-policy status, deduplication evidence, inventory-based form/attachment/composer states, actual returned links, current user actions, writes actually read back, and pending sync items. Distinguish a historical receipt from a fresh live check, an application from a referral, and a draft from a send or submission.
- State the evidence level accurately: candidate instructions implemented, host-reviewed candidate installed, and live operational behavior proved are distinct claims. This procedure alone proves none of the last two.

For controlled regression scenarios—other-tab research, reset/restore, recipient-count reconciliation, visible retention marks, and later-turn survival—use [browser handoff validation](browser-handoff-validation.md). It is a host-run fixture protocol, not permission to perform browser work or proof of any live ATS, LinkedIn, or Terra behavior.

## Failure-driven examples

- **Search only:** return verified roles and fit evidence; a read-only ATS inspection is allowed to verify the destination, but no fields, uploads, or drafts are changed.
- **Selected AI role with a technical caveat:** retain and prepare the selected role; record the caveat without recategorizing ordinary technical collaboration as excluded data-centric work.
- **Authorized form plus three explicitly requested LinkedIn invitations with no known mutual:** record separate relationship checks as no recorded or visible mutual evidence, retain the form and three named invitation inventory rows, and prepare neutral invitations without waiting for an introduction answer.
- **Missing mandatory answer:** fill independent fields and requested drafts, mark the required field `blocked`, and ask one concise batch question rather than guessing.
- **LinkedIn blank while the ATS is usable:** stop all LinkedIn activity without reload or workaround, retain the actual LinkedIn error category/page condition, continue the form and authorized records, and report the affected composers as blocked or unverified.
- **Five visible invitation tabs from an expected eight:** reconcile the named three absent items individually; do not call the five a complete set or recreate an invitation without the applicable scope and no-stop condition.
